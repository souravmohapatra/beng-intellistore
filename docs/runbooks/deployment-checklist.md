The implementation and local proofs below are not deployment acceptance.
The remaining steps need the real machines, independent labels/oracles or your
physical device. Follow them yourself, or explicitly authorize an agreed subset.
Existing dashboard/search/source access does not depend on advice being enabled.

## 1. Laptop inference runtime (tasks05/06/08)

Follow `docs/runbooks/inference-runtime.md`:

1. Confirm NVIDIA container GPU access and free disk.
2. Start `compose.inference.yaml`, pull at most two candidates, record digests.
3. Obtain one real structured response from the worker container with
   `--check-inference`, leaving `INFERENCE_ENABLED=false`.
4. Run `scripts/advice_benchmark.py` inside the worker container with at least
   50 independently labelled held-out cases and a separate100-item warm workload.
   Require both quality and error-free warm-time gates; record cold-load time
   and GPU memory. The runbook gives the Docker invocation.
5. Only after that recorded pass, set `INFERENCE_ENABLED=true` in both the
   mini-PC application runtime file and laptop worker runtime file. Restart
   both corresponding services, then request and confirm a source-linked
   suggestion end to end. It must change nothing before explicit acceptance.
6. If no candidate passes, keep `INFERENCE_ENABLED=false`; report the result for
   an explicit scope decision.

## 2. NAS backup and restore (tasks10/13)

Follow `docs/runbooks/backup-restore.md`:

1. Set `INTELLISTORE_BACKUP_DIR` and `INTELLISTORE_RESTORE_DIR`; confirm writable
   uid and headroom. Status is written inside `INTELLISTORE_HOST_DATA_DIR/status`.
2. Install `intellistore-backup.service`/`.timer`; run one controlled generation.
3. Confirm the Status page shows success and seven-generation retention.
4. Make the destination unavailable once; confirm failure visibility, no local
   deletion, no good generation retired, and normal app use.
5. Restore the generation into a new database + empty originals directory; verify
   through a temporary app (dashboard, search, original bytes, corrections).
6. Record timings, counts, recovery window and limitations.

## 5. Performance measurement (task15)

On an isolated mini-PC benchmark copy:

```bash
# Requires an already-created/migrated isolated intellistore_benchmark database
# in the separately approved benchmark stack, never the production stack:
docker compose -p intellistore-benchmark -f compose.production.yaml \
  run --rm --entrypoint python -e POSTGRES_DB=intellistore_benchmark app \
  manage.py seed_benchmark_data --confirm-isolated
# On the browser measurement client:
pip install -r requirements-benchmark.txt && python -m playwright install chromium
INTELLISTORE_BENCH_PASSWORD=... python scripts/browser_latency_benchmark.py \
  --base-url http://<mini-pc>:8017 --username <user> --runs 30 \
  --month 2026-08 --output ~/private/latency-browser.json
```

Require p95 ≤ 2s for dashboard, period submit and search; record cold
load, dataset/browser/network/runtime. `scripts/latency_benchmark.py` measures
HTTP response only and is diagnostic, not the acceptance gate. Never seed the
live database.
